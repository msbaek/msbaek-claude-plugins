# 장바구니 — tdd-plan 입력 문서 (요구사항 정리 템플릿 + 예제)

> **이 문서의 역할**: `/tdd-plan`에 **참조로 전달하는 요구사항 원천 문서**다.
> (`/tdd-plan`의 **인자**는 `/tdd`가 만드는 작성 대상 템플릿 문서다 — 이 문서가 아니다.)
> tdd-plan이 이 문서를 읽고 단계 1(도메인 규칙 + User Story)부터 시작할 수 있도록,
> 스킬이 소비하는 구조에 맞춰 원천 자료를 미리 정리해 둔다.
>
> **템플릿으로 쓰는 법**: 각 섹션 첫머리의 인용 블록(>)이 작성 지침이고, 그 아래
> 본문이 장바구니 도메인으로 채운 예제다. 새 기능에 쓸 때는 지침을 남기고 본문만
> 교체한다.
>
> **여기에 없는 것**: User Story 완성형·Gherkin·unit test 목록. 그 형식화는
> tdd-plan이 사용자 피드백을 받으며 수행하는 일이므로, 이 문서는 **재료까지만**
> 제공한다. 완성형을 미리 쓰면 스킬의 피드백 루프(INVEST 점검, 핵심 예시 선정)를
> 건너뛰게 된다.

## tdd-plan 소비 매핑

| 이 문서의 섹션 | tdd-plan이 사용하는 곳 |
|---|---|
| §1 범위와 유형 | 템플릿 선택(web-app 여부), Web App 추가 단계(E-1/E-2) 진행 여부 |
| §2 도메인 규칙(0층) | 단계 1a — 거의 그대로 전사 (이 문서의 "예제" = tdd-plan의 "검산 전개", 숫자의 정본) |
| §3 액터와 가치 | 단계 1b — User Story 형식화 + INVEST 점검의 재료 |
| §4 경계 조건 후보 | 단계 2 — Gherkin 핵심 예시 선정 (경계 조건 식별 가이드 대응) |
| §5 흐름·상태 신호 | (조건부) Use Case 추가 판단 체크리스트의 근거 |
| §6 미확정 사항 | 단계 1 진행 전 사용자에게 질문할 목록 |

## 1. 범위와 유형

> 다룰 기능을 나열하고, 각 기능의 성격(순수 계산 / 상태 전이 + 협력 객체)을
> 표시한다. 실제 운영 도메인에서 **의도적으로 들어낸 것**도 반드시 적는다 —
> 적지 않으면 tdd-plan이 "누락된 요구사항"으로 오인해 질문하거나 시나리오를
> 지어낸다(invent)[^invent]. TDD 유형(java, web-app 등)이 미정이면 미정이라고 쓴다.

ktown4u 장바구니 도메인에서 두 기능만 다룬다:

1. **합계 계산** — 장바구니 금액 산출. 부수효과 없는 순수 계산.
2. **주문 전환(체크아웃)** — 장바구니를 주문으로 전환. 상태 전이 + 협력 객체
   (재고, 주문 생성).

**TDD 유형**: 미정 — 도메인 로직만 검증하려면 `java`(순수 단위 테스트),
HTTP 관통까지 포함하려면 `web-app`(Cucumber 인수 테스트 + Walking Skeleton 필수).
tdd-plan 시작 시 결정한다.

**의도적으로 제외한 것** (실제 운영 도메인에는 있지만 계산·상태 규칙과 무관한
운영 복잡도):

- 수량 제한 3계층과 그 게이팅 조건(CN상점 + YTO배송 + CN배송국가)
- 레거시/신규 병행 저장(dual-write), 논리삭제
- 게스트 카트, 팬클럽 추가구성품
- 세금(GST/VAT), 배송 불가 지역·연령 제한

## 2. 도메인 규칙 (0층)

> tdd-plan 단계 1a가 요구하는 구조 그대로 쓴다: **기본 규칙 / 특별 규칙 /
> 예제**. 규칙(스펙)은 그 자체로는 이해가 어렵다 — 특별한 경우를 구체 수치로
> 보여주는 예제가 있어야 이해가 쉬워진다(Specification by Example, Emily Bache
> "Usage First Design in TDD"). 계산 도메인이면 예제의 수치를 반드시 **사람이
> 손으로 직접 계산해 확인**해 둔다 — **이 수치가 이후 모든 기대값(Gherkin Examples,
> unit test assert)의 단일 출처(정본)다.** AI가 생성한 수치를 정본으로 삼지
> 않는다.

### 2a. 합계 계산

- 기본 규칙
    - 장바구니는 0개 이상의 라인을 가진다. 라인 = (상품, 단가, 수량). 수량 ≥ 1.
    - **상품 합계** = 모든 라인의 (단가 × 수량) 합.
    - **배송비**는 주문당 고정 3,000원. 단, 빈 장바구니는 배송비도 0원.
    - 모든 금액은 원 단위 정수이며 음수가 될 수 없다.
- 특별 규칙 — 할인 적용 순서가 불변식
    - 적용 순서: **상품 합계 → 쿠폰 할인 → 마일리지 차감 → 배송비 합산**
    - **쿠폰 할인(1단계)**: 상품 합계에서 차감. 쿠폰 금액이 상품 합계를 초과하면
      상품 잔액은 0원까지만 내려간다(초과분 소멸).
    - **마일리지 차감(2단계)**: 쿠폰 적용 **후 잔액** 기준으로 차감.
        - 먼저 상품 잔액에서 차감한다.
        - 상품 잔액이 0원에 도달하면, **남은 마일리지는 배송비에서 추가 차감**한다.
        - 배송비도 0원에 도달하면, 그 이상의 마일리지는 사용되지 않는다
          (소멸이 아니라 미사용 — 차감 상한).
    - **최종 결제 금액** = 상품 잔액 + 배송비 잔액. 항상 ≥ 0.

#### 예제 (사람이 계산한 정본 수치)

**예제 1 — 기본 흐름**

| 단계 | 계산 | 결과 |
|---|---|---|
| 상품 합계 | 10,000×2 + 5,000×1 | 25,000 |
| 쿠폰 5,000 | 25,000 − 5,000 | 20,000 |
| 마일리지 3,000 | 20,000 − 3,000 | 17,000 |
| 배송비 | 17,000 + 3,000 | **20,000** |

**예제 2 — 상품가 0원 도달, 마일리지가 배송비로 넘어감**

| 단계 | 계산 | 결과 |
|---|---|---|
| 상품 합계 | 8,000×1 | 8,000 |
| 쿠폰 5,000 | 8,000 − 5,000 | 3,000 |
| 마일리지 4,000 | 상품 3,000 → 0, 잔여 1,000은 배송비로 | 상품 0 |
| 배송비 | 3,000 − 1,000 | 2,000 |
| 최종 | 0 + 2,000 | **2,000** |

**예제 3 — 마일리지 차감 상한 (상품·배송비 모두 0)**

| 단계 | 계산 | 결과 |
|---|---|---|
| 상품 합계 | 8,000×1 | 8,000 |
| 쿠폰 5,000 | 8,000 − 5,000 | 3,000 |
| 마일리지 10,000 | 상품 3,000 → 0, 배송비 3,000 → 0, 잔여 4,000 미사용 | 0 |
| 최종 | 0 + 0 | **0** |

**예제 4 — 빈 장바구니**

상품 합계 0, 배송비 0 → 최종 **0**.

**예제 5 — 쿠폰이 상품 합계 초과**

상품 합계 3,000, 쿠폰 5,000 → 상품 잔액 0(−2,000 아님), 마일리지 없음,
배송비 3,000 → 최종 **3,000**.

> 확인: 위 예제 수치는 사용자가 계산해 확인한 값이다.

### 2b. 주문 전환(체크아웃)

- 기본 규칙
    - 상태는 두 가지: `ACTIVE`(담기·계산·전환 가능), `ORDER_CREATED`(전환 완료,
      더 이상 전환 불가).
    - 전환 성공 조건 세 가지가 **모두** 충족되어야 한다:
        1. 장바구니가 비어 있지 않다.
        2. 모든 라인의 요청 수량 ≤ 해당 상품 재고.
        3. 장바구니 상태가 `ACTIVE`다.
    - 성공 시 세 가지가 **함께** 일어난다: 주문 생성, 상태 `ACTIVE` →
      `ORDER_CREATED` 전이, 라인 수량만큼 재고 차감.
    - **불변식: 한 장바구니는 한 번만 주문으로 전환된다.**
- 특별 규칙 — 실패 시 아무것도 변하지 않는다
    - 재고 부족(한 라인이라도): 전환 실패. 주문 미생성, 상태 `ACTIVE` 유지,
      재고 변화 없음.
    - 빈 장바구니: 전환 거부.
    - 이미 `ORDER_CREATED`인 장바구니: 전환 거부 (중복 주문 방지).

#### 예제 (사람이 계산한 정본 수치)

**예제 6 — 전환 성공**: 상품 A 수량 2(재고 10), 상태 ACTIVE → 주문 생성,
상태 ORDER_CREATED, 재고 10 → 8.

**예제 7 — 재고 부족**: 상품 A 수량 5(재고 3) → 실패. 주문 없음, 상태
ACTIVE, 재고 3 유지.

> 확인: 위 예제의 상태 전이 결과는 사용자가 확인한 값이다.

## 3. 액터와 가치 (User Story 재료)

> 완성된 User Story를 쓰지 않는다 — 역할·원하는 것·가치의 **재료**만 나열한다.
> `So that`(얻는 가치)을 채울 수 없는 항목은 스토리가 아니라 작업 지시이므로,
> 여기서 미리 가치를 확인해 둔다. 형식화·INVEST 점검은 tdd-plan 단계 1b의 일이다.

| 기능 | 역할 | 원하는 것 | 얻는 가치 |
|---|---|---|---|
| 합계 계산 | 장바구니에 상품을 담은 고객 | 쿠폰·마일리지가 반영된 최종 결제 금액을 아는 것 | 직접 계산하지 않아도 결제 전에 부담액을 알고 구매를 결정 |
| 주문 전환 | 구매를 결정한 고객 | 장바구니를 주문으로 확정하는 것 | 담은 상품을 재고가 확보된 상태로 구매 완료 |
| 주문 전환(실패 측면) | 고객 | 재고 부족 시 부분 주문이 생기지 않는 것 | 일부만 주문되는 예상 밖 결과를 겪지 않음 |

## 4. 경계 조건 후보

> tdd-plan의 "경계 조건 식별 가이드" 5분류에 맞춰, 이 도메인에서 걸리는 경계를
> 미리 나열한다. 여기 적은 것이 단계 2 Gherkin 핵심 예시 선정의 후보 목록이 된다.
> 이미 예제로 덮인 것은 예제 번호를 적고, 덮이지 않은 것은 "예제 없음"으로
> 표시해 tdd-plan이 수치를 지어내지 않고 사용자에게 계산을 요청하게 한다.

1. **수치적 경계**
    - 쿠폰 = 상품 합계 정확히 일치 (잔액 0, 초과분 없음) — 예제 없음
    - 쿠폰 > 상품 합계 (초과분 소멸) — 예제 5
    - 마일리지 = 쿠폰 적용 후 잔액 정확히 일치 (배송비 침범 직전) — 예제 없음
    - 마일리지 > 상품 잔액 (배송비로 넘어감) — 예제 2
    - 마일리지 > 상품 잔액 + 배송비 (차감 상한, 최종 0원) — 예제 3
2. **크기 경계**
    - 빈 장바구니로 합계 계산 — 예제 4
    - 빈 장바구니로 주문 전환 거부 — 예제 없음
    - 라인 1개 (최소 유효 장바구니) — 예제 2·3·5
3. **상태 경계**
    - `ACTIVE` → 전환 성공 — 예제 6
    - `ORDER_CREATED` → 전환 거부 (중복 주문 방지) — 예제 없음
    - 요청 수량 = 재고 정확히 일치 (재고 0으로 소진) — 예제 없음
4. **시간·순서 경계**
    - 할인 적용 순서 불변식 (쿠폰 먼저, 마일리지 나중) — 순서를 바꾸면 결과가
      달라지는 입력이 존재하는가? — 예제 없음
5. **집계 경계** — 같은 키가 여러 항목으로 나뉘는 경우
    - 같은 상품이 두 라인으로 담긴 장바구니 + 재고 검증: 라인별 검증은 통과하지만
      합산하면 재고 초과인 입력 (예: A 2개 + A 2개, 재고 3) — **원본 자료에
      미규정. §6 미확정 사항 참조**

## 5. 흐름·상태 신호 (조건부 Use Case 판단 재료)

> tdd-plan은 "판단 체크리스트 4항목 중 2개 이상이면 Use Case를 추가"한다.
> 각 항목에 해당하는 사실이 이 도메인에 있는지만 기록한다 — 판단은 tdd-plan에서.

| 체크리스트 항목 | 이 도메인의 사실 |
|---|---|
| 액터 2명 이상 + 관심사 충돌 | 아니오 — 고객 단일 액터 |
| 상태 전이 | 있음 — `ACTIVE` → `ORDER_CREATED` (단방향, 1회) |
| 대안·예외 흐름 3개 이상 | 있음 — 재고 부족 / 빈 장바구니 / 중복 전환 (3개) |
| 기능 간 불변식 | 있음 — 합계 계산이 보여준 금액 = 주문 전환이 확정하는 금액 (단, 원본 자료에 명시 규정은 없음 — §6 참조) |

## 6. 미확정 사항 (tdd-plan 시작 전 결정 필요)

> 모호한 채 tdd-plan에 들어가면 스킬이 추측하거나 매 단계 질문이 반복된다.
> 결정할 사람이 결정할 질문을 여기 모아 둔다. "제외"도 결정이다 — 결정했으면
> §1의 제외 목록으로 옮긴다.

1. **같은 상품 복수 라인 허용 여부** — 허용한다면 재고 검증은 라인별인가
   상품별 합산인가? (합산이 아니면 §4-5의 오버셀 입력이 통과한다. 허용하지
   않는다면 "장바구니 안에서 상품은 유일하다"를 §2 기본 규칙으로 승격)
2. **전환 시점의 금액 재계산 여부** — 주문 전환 시 합계 계산을 다시 수행해
   주문 금액으로 기록하는가, 아니면 이 예제에서 주문은 금액 없이 생성되는가?
   (§5의 "기능 간 불변식" 성립 여부가 이 결정에 달려 있다)
3. **TDD 유형** — `java`(도메인 로직만) vs `web-app`(HTTP 관통 + Cucumber 필수).

## 용어집

### 예제(example)

규칙(스펙)을 설명하는 구체 사례. 규칙은 그 자체로는 이해가 어렵고, 특별한
경우를 구체 수치로 보여주는 예제가 있어야 이해가 쉬워진다(Specification by
Example — Emily Bache, "Usage First Design in TDD, By Example"). 요구사항 →
예제 → 테스트 케이스 순서로, 예제가 곧 테스트 케이스 목록의 원천이 된다.

예제의 수치는 **사람이 손으로 직접 계산해 확인한 값**이어야 정본(숫자의 단일
출처)이 된다 — AI가 만든 수치는 사람이 확인하기 전까지 정본이 아니다(아래
"지어내다" 2번 참조). 이 문서의 "예제 없음" 표시는 "규칙만 있고 사람이 계산한
수치가 아직 없다"는 뜻이다.

(tdd-plan 스킬은 같은 산출물을 "검산 전개"라고 부른다 — 이 문서의 §2 예제가
그 자리에 들어간다.)

### 지어내다(invent)

**원천 자료에 없는 요구사항을 AI가 그럴듯하게 만들어 채워 넣는 것.**
환각(hallucination)의 요구사항 버전이다. tdd-plan 스킬 본문에도 같은 개념이
나온다 — "인수 조건에 없는 API를 발명하지 않는다".

AI 입장에서는 원천 자료의 빈칸이 "누락"인지 "의도적 제외"인지 구분되지 않는다.
그래서 빈칸을 만나면 학습한 일반 도메인 지식으로 그럴듯하게 채우려 한다.
이 도메인에서 일어날 수 있는 세 가지 형태:

1. **시나리오를 지어냄** — "장바구니라면 당연히 있겠지"를 채운다.
   원천 자료에 없는 세금 계산·게스트 카트·수량 제한 시나리오를 생성.
   → §1의 "의도적으로 제외한 것" 목록이 방어한다: AI가 목록을 보고
   "없는 게 맞다"고 판단할 수 있다.
2. **수치를 지어냄** — 예제 없는 경계의 기대값을 AI가 계산해 Examples 표에
   넣는다. 값이 맞더라도 **정본이 사람 계산이 아니라 AI 계산이 된다**는 게
   문제다 — AI가 규칙을 잘못 해석해 계산했다면, 틀린 구현이 틀린 기대값을
   통과해 초록불이 된다.
   → §4의 "예제 없음" 표시가 방어한다: 값을 지어내는 대신 사용자에게 계산을
   요청하게 한다.
3. **인터페이스를 지어냄** — 시나리오가 요구하지 않는 API를 테스트 편의로
   만든다(예: 모든 시나리오가 "이미 담긴 장바구니"에서 시작하는데 생성 POST
   API를 만듦). 아무도 요청하지 않은 계약을 이후 계속 유지·검증해야 하는
   부채가 된다.
   → tdd-plan 단계 E-2의 "인수 조건에 없는 API를 발명하지 않는다" 규칙이
   방어한다.

공통 구조와 원칙:

```
원천 자료의 빈칸
  → AI가 일반 지식으로 그럴듯하게 채움 (= 지어냄)
  → 지어낸 요구사항이 테스트·코드가 됨
  → 아무도 요청하지 않은 것을 구현·유지하게 됨
```

**빈칸을 발견하면 채우지 말고 사람에게 물어라.** 이 문서의 §1 제외 목록,
§4 예제 없음 표시, §6 미확정 사항이 모두 이 원칙의 장치다.

[^invent]: 원천 자료에 없는 요구사항을 AI가 그럴듯하게 만들어 채워 넣는 것.
    시나리오·수치·인터페이스 세 형태가 있다. 상세는 하단 [용어집](#용어집) 참조.
