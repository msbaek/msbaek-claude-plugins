# 적대적 리뷰 (정본)

`tdd-rgb`, `tdd-feature`가 공유하는 절차의 정본이다.

## 언제 실행하는가

다음 **둘 중 하나**에 해당하면, 전체 테스트 목록이 green이 된 뒤 최종 사용자 검토
**전에** 반드시 실행한다:

- 기어가 high다 (검토 지점이 최종 1회뿐이라 중간 검증이 없다)
- 기어와 무관하게 폭발 반경 high-stakes가 감지됐다 (틀렸을 때의 비용이 크다)

`tdd-feature`의 Phase B는 그 자체가 high이므로 항상 해당한다.

**사람 검토는 이것을 대체하지 못한다.** 사람 검토는 "이 코드가 맞는가"를 묻고,
적대적 리뷰는 "green인데도 검증되지 않은 경로가 어디인가"를 묻는다. 후자는 통과한
테스트만 보고 있으면 보이지 않는다.

## 리뷰어 선택

1. 환경에 `adversarial-reviewer` agent가 있으면 그것으로 dispatch (1순위)
2. 없으면 general-purpose sub-agent에 아래 내장 프롬프트로 dispatch

내장 프롬프트 (fallback):

> 당신은 이 diff를 깨뜨리려는 적대적 리뷰어입니다. 평가하지 말고 공격하세요.
> 다음을 찾아 심각도(critical/major/minor)와 함께 보고하세요:
> 1. 테스트가 검증하지 않는 동작 (green이지만 커버되지 않은 경로)
> 2. 테스트 목록 문서와 구현의 표류(drift)
> 3. 최소 구현을 가장한 과잉 구현 (테스트가 요구하지 않는 코드)
> 4. 코드 스멜 (중복, 불명확한 이름, 긴 메소드)
> 각 지적에 구체적 실패 시나리오("이게 일어나면 → 저게 깨진다")를 붙이세요.

## 입력

- 진행 기록의 시작 커밋..HEAD diff (`git diff {시작커밋}..HEAD`)
- 테스트 목록 문서 (intent 요약 — 리뷰어의 depth 보정에 사용)

**리뷰 diff는 전체 구현을 포함해야 한다.** 기준점이 되는 시작 커밋 해시는 적대적
리뷰가 예정된 시점(high 기어 시작, 또는 폭발 반경 감지)에 진행 기록에 남긴다
(`references/gears.md`의 "기어 기록" 참조). Web App이라면 추가 단계(인수 테스트 완료
확인·JPA Repository 완성·DSL 개선)까지 마친 뒤 리뷰를 실행한다.

## 결과 처리

1. 지적 사항을 심각도별로 분류해 사용자에게 보고
2. 수정이 필요한 항목은 사용자 승인 후 반영 — 반영도 RGB 규칙 준수 (실패 테스트 먼저)
3. 리뷰 통과 후에야 최종 사용자 검토를 요청
   - **통과 기준**: critical/major 지적이 모두 해소(수정 반영 또는 사용자가 명시적으로
     수용)된 상태

green 스위트 + 적대적 리뷰 통과가 이 경우의 Definition of Done이다.
