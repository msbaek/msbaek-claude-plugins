# 기어 운용 — 전환 신호·폭발 반경·기어 기록 (정본)

기어별 검토 지점 표와 진행 표기 규칙은 `SKILL.md` 본문에 있다(사이클마다 필요하므로).
이 문서는 **시작 시 1회**와 **사이클 경계 점검 시**에만 필요한 부분을 담는다.

## 호출 형식 — 기어별

```
/tdd-rgb                        # 기어 기록 있으면 복원, 없으면 low
/tdd-rgb --gear=low             # 매 R/G/B phase마다 검토 (기본)
/tdd-rgb --gear=mid             # 테스트 1개의 R→G→B 완료 후 검토
/tdd-rgb --gear=high            # 전체 완료 + 적대적 리뷰 후 최종 검토
/tdd-rgb {plan경로} --gear=mid  # plan 문서를 명시할 때
```

`--gear` 미지정 시: 템플릿 문서 진행 기록에 기어 기록이 있으면 그 기어로 복원, 없으면 low.
`--gear`로 명시 지정하면 문서의 기존 기록보다 우선한다.

## tdd-feature와의 관계

| 원하는 검토 밀도 | 호출 |
|---|---|
| low·mid (단계별·사이클별 검토) | `/tdd-rgb --gear=low` 또는 `--gear=mid` |
| high, **테스트 목록 전체**를 자율로 | `/tdd-rgb --gear=high` |
| high, **feature 하나**를 plan 합의 후 자율로 | `/tdd-feature` (Phase B가 feature 범위 high 기어) |

`/tdd-feature`는 `--gear`를 받지 않는다 — Phase B 자체가 high다. 대신 high의 안전장치
(폭발 반경 점검·시작 커밋 기록·적대적 리뷰)를 동일하게 적용한다. low·mid가 필요하면
`/tdd-feature`가 아니라 `/tdd-rgb`를 쓴다.

## 기어 전환 — 신호와 제안

사이클 사이에 아래 신호를 점검하고, 감지 시 전환을 **제안**한다. 결정은 항상 사용자.

**업시프트 신호** (low→mid, mid→high):

- 최근 2~3 사이클 연속 사용자 피드백이 "그대로 진행"뿐이었음
- Blue phase에서 새로운 통찰이 더 이상 나오지 않음 (설계 안정)
- 남은 테스트가 기존 패턴의 반복

업시프트 제안 문구에 반드시 포함: "지루함은 업시프트를 얻어냈다는 정직한 신호지만, 조급함은 그렇지 않습니다."

**업시프트 억제 조건** (위 신호가 있어도 제안하지 않음):

- 슬라이스가 테스트가 얇은 기존 코드에 걸쳐 있음 — 새로 작성하는 코드는 TDD 3법칙으로
  테스트가 보장되지만, 설명 기반 이해(mid/high의 이해 채널)는 검증 압력(테스트 스위트)이
  받쳐줄 때만 신뢰할 수 있다. 설명은 생성물이라 그럴듯하게 틀릴 수 있기 때문
- 대상이 오래 유지보수할 핵심 도메인 — 이해 자체가 산출물이므로 속도가 가능해도
  low~mid를 유지한다 (주변부·보일러플레이트는 high 적합). 이 조건은 mid→high만 막고
  low→mid는 허용한다. 핵심 도메인 해당 여부가 불확실하면 사용자에게 확인

억제 조건은 **제안**만 막는다 — 사용자가 직접 기어를 지정하면 억제 사유를 한 줄로
안내한 뒤 지정을 따른다 (폭발 반경 경고와 동일한 방식).

**다운시프트 신호** (high→mid, mid→low):

- revert 발생
- 예상과 다른 이유의 테스트 실패 반복
- 구현이 불투명 — 사용자 이견·질문 반복
- Green phase에서 최소 구현 범위를 넘는 코드 생성 감지

**다운시프트 전 설명 단계** (이해 결손 계열 신호에만 적용):

이해 결손 계열 신호(구현 불투명, 이견·질문 반복)가 감지되면 다운시프트를 바로 제안하지
않고, 먼저 사용자가 원하는 고도의 설명을 제공한다(예: "이 슬라이스 흐름을 의사 코드로").

- 설명으로 놀라움이 해소되면 → 기어 유지
- 설명과 실제 행동(테스트 결과·diff)이 어긋나면 → 다운시프트 제안

실패 계열 신호(revert 발생, 예상 밖 테스트 실패 반복)는 설명 없이 바로 다운시프트를
제안한다 — 검증기가 이미 이론의 결함을 증명했기 때문.

## 폭발 반경(blast radius) 경고

시작 시와 업시프트 제안 전에 대상 코드 영역에서 high-stakes 신호를 점검한다:
인증/인가, 결제/금액 계산, 데이터 삭제·변경(마이그레이션), 외부 API 호출, 동시성.

감지 시 처방은 **둘**이다. 하나는 사용자가 결정하고, 하나는 기어와 무관하게 실행된다:

1. **기어 권장(사용자 결정)** — "이 작업은 폭발 반경이 큽니다({영역}). 확신이 높아도
   한 단 낮은 기어를 권장합니다. 틀릴 확률이 낮아도 틀렸을 때 비용이 큽니다."
   경고 후 결정은 사용자. high-stakes 영역에서는 업시프트 제안을 억제한다
   (다운시프트 제안은 정상 동작).
2. **적대적 리뷰 1회(기어 무관, 협상 대상 아님)** — "그리고 어느 기어로 진행하든
   전체 완료 시 적대적 리뷰를 1회 실행합니다." `references/adversarial-review.md` 참조.

**두 축을 분리하는 이유**: 기어는 *검토 밀도*를 정하고 폭발 반경은 *틀렸을 때의 비용*을
정한다 — 다른 축이다. 낮은 기어의 단계별 사람 검토는 적대적 리뷰를 대체하지 못한다.
사람 검토는 "이 코드가 맞는가"를 묻고, 적대적 리뷰는 "green인데도 검증되지 않은 경로가
어디인가"를 묻기 때문이다. 후자는 통과한 테스트만 보고 있으면 보이지 않는다.

폭발 반경이 감지되면 **기어와 무관하게 현재 HEAD 해시를 진행 기록에 남긴다** —
적대적 리뷰의 입력이 `시작 커밋..HEAD` diff이므로 기준점이 없으면 리뷰를 실행할 수 없다.

## 기어 기록

템플릿 문서 진행 기록 섹션에 현재 기어와 전환 이력을 남긴다:

```
기어: mid (사이클 7에서 low→mid, 사유: 설계 안정)
```

기어 변경(시작 지정 포함) 시마다 갱신한다. **적대적 리뷰가 예정된 경우** — high 기어
자율 진행 시작 시, 또는 기어와 무관하게 폭발 반경 high-stakes가 감지된 시점 — 현재 HEAD
해시도 함께 기록한다 (적대적 리뷰 diff 기준점):

```
기어: high (사이클 12에서 mid→high, 사유: 남은 테스트가 패턴 반복) / 시작 커밋: abc1234
기어: low (폭발 반경 high-stakes: 금액 계산 — 완료 시 적대적 리뷰) / 시작 커밋: def5678
```

**폭발 반경이 사이클 도중 처음 감지되면**(그 영역에 이제야 진입) 두 처방을 그때
적용하고, diff 기준점은 **이 작업의 첫 커밋의 부모**를 남긴다 — 감지 시점 HEAD를
남기면 리뷰 diff가 그 이전 구현을 놓친다. 이미 기록된 기준점이 있으면 갱신하지 않는다.
