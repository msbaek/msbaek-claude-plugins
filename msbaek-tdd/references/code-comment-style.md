# 코드 주석 스타일 (정본)

msbaek-tdd가 생성·수정하는 Java 코드에 적용한다. 코드를 쓰는 모든 에이전트
(`tdd-red`·`tdd-green`·`tdd-blue`·`tdd-skeleton-builder`·`tdd-acceptance-builder`)가
이 문서를 참조하며, 각자 재기술하지 않는다.

## 왜 한글인가

이 워크플로우의 주석은 "무엇을 하는 코드인가"가 아니라 **왜 이렇게 결정했는가**를 담는다.
근거의 출처가 앵커 문서(`{ClassName}.md`)이므로 성격이 코드보다 그 문서에 가깝다.
앵커가 한글인데 주석만 영어면 같은 근거를 두 언어로 읽게 되고, 앵커와 대조할 때마다
번역을 한 번 거친다.

## 규칙

1. **소스 주석은 한글로 쓴다** — 클래스·메서드 Javadoc, 인라인 주석, 단정(assertion)
   메시지, 예외 메시지.
2. **모호할 수 있는 용어는 `한글(english)` 병기** — 괄호 앞 공백 없음.
   예: 이음매(seam), 관리 상태(managed), 표현 선택(presentation choice),
   왕복 보존(round-trip), 공허한 단정(vacuous assertion), 실패 주입(failure injection).

## 번역하지 않는 것 (grep이 끊긴다)

- 식별자·타입·메서드명, API 경로, 애노테이션
- 프레임워크·JPA 용어가 **코드 이름으로 등장할 때**: `@Transactional`, dirty checking,
  auto-flush, detached, LAZY, OSIV 등. 본문에서 **설명할 때**는 규칙 2대로 병기한다
  (예: "지연 로딩(LAZY) 경계를 트랜잭션 안에서 닫는다").
- `@DisplayName` — 이미 한글이므로 그대로 둔다.

## 전환 예

```java
// before
// Anchor rule 7: validation order is an invariant - 404 -> 403 -> 409

// after
// 검증 순서가 불변식이다 — 404 → 403 → 409 순으로 검사하고
// 먼저 걸리는 사유로 거부한다
```

## 규칙 번호를 인용하지 않는다 — 내용을 그 자리에 적는다

`(앵커 규칙 5)`, `앵커 규칙 3/7-②:` 같은 번호 인용은 두 가지로 실패한다.

- 읽는 사람이 무슨 규칙인지 알려면 앵커 문서를 열어야 한다. 프로덕션 코드가 test 경로의
  `.md`를 가리키는 것도 어색하다.
- 앵커에서 규칙이 하나 추가·삭제되면 번호가 밀려 코드의 모든 참조가 **조용히** 다른 규칙을
  가리킨다. 컴파일러도 테스트도 잡지 못한다. 식별자는 rename이 따라가지만 "규칙 5"는
  아무도 고치지 않는다.

| before | after |
|---|---|
| `// 앵커 규칙 7: 검증 순서가 불변식이다 — 404 → 403 → 409 …` | `// 검증 순서가 불변식이다 — 404 → 403 → 409 …` (번호만 삭제) |
| `앵커 규칙 4(환불 요청액 = 결제액)가 결제액의 존재를 전제한다` | `환불 요청액 = 결제액이므로 결제액이 반드시 있어야 한다` |
| `앵커 규칙 3/7-②: 요청자가 이 주문의 소유자여야 한다` | 주석 삭제 (메서드명 `isOwnedBy`가 이미 말한다) |

**정본 위치는 패키지에 한 번만** — `package-info.java`에 "실행 정본 = `.feature`, 서술
정본 = `{ClassName}.md`"와 "개별 클래스 주석은 규칙 번호를 인용하지 않는다"는 이유 한 줄을
둔다. 10곳이 각자 가리키는 대신 한 곳에서.

## 코드가 이미 말하는 것은 다시 말하지 않는다

`record CancelOrderResponse(...)`에 "POST …의 응답 DTO"를 붙이지 않는다 — 이름과 선언이
이미 말한다. 주석이 없는 편이 더 깔끔한 자리가 많다.

**설명은 결정을 내린 자리에 둔다.** 엔티티 대신 DTO를 반환하기로 한 이유(OSIV·지연
로딩(LAZY) 경계)는 그 결정을 내린 컨트롤러에 쓴다. 결정하지 않은 쪽(결과물인 DTO)에 두면
그 클래스가 왜 존재하는지가 아니라 남의 결정을 설명하게 된다.

## 번역투 대신 실제 쓰는 말

영어 관용어를 직역해 만든 합성어는 한국어 독자에게 통하지 않는다. 그 도메인에서 실제로
쓰는 말을 쓰고, 원어가 필요하면 규칙 2대로 `한글(english)`로 붙인다.

| 직역(쓰지 않음) | 쓸 말 |
|---|---|
| 와이어 계약 | API 응답 계약, 응답 본문 |
| 와이어 포맷 | 직렬화 포맷 |
| 와이어 본문 그대로 | 직렬화된 본문 그대로(raw), 실제 응답 본문 |

## 비유 대신 관측 가능한 결과로 쓴다

"잠근다(lock)"처럼 자물쇠에 빗대는 표현은 실제로 무슨 일이 일어나는지 말해주지 않는다.
기본 표현은 **"테스트가 커버한다"**이고, 보장의 강도를 설명해야 하는 자리에서만
**무엇이 어떻게 되면 무엇이 실패하는지**로 쓴다.

| 비유(쓰지 않음) | 쓸 표현 |
|---|---|
| 승인 파일이 응답 형식을 잠근다 | 응답 본문 전체를 테스트가 커버한다 |
| `ExplicitSaveGuardTest`가 이 규약을 잠근다 | 이 규약은 `ExplicitSaveGuardTest`가 커버한다 |
| (강도를 말해야 할 때) | 이 호출을 지우면 `ExplicitSaveGuardTest`가 실패한다 |
| raw 구획이 fidelity를 지킨다 | 직렬화 형식이 바뀌면 raw 구획이 깨진다 |

**TDD 색깔을 행위 주체로 쓰지 않는다.** 색이 무언가를 드러내거나 증명할 수는 없다.

| 쓰지 않음 | 쓸 표현 |
|---|---|
| Red가 드러냈다 | 테스트 실패로 드러냈다 |
| Green이 증명한다 | 이 테스트가 통과하는 것으로 확인된다 |

테스트의 **상태**를 말하는 것은 그대로 둔다 — "InMemory 쪽만 red, JPA 쪽 green 유지",
"전체 스위트 green". 금지 대상은 색을 주어로 세워 행동을 시키는 것이다.

## 빌드 인코딩 (한글은 주석뿐 아니라 문자열 리터럴에도 들어간다)

프로젝트 골격을 새로 만들거나 빌드 파일을 손볼 때 컴파일 인코딩을 **명시**한다.
플랫폼 기본 인코딩에 기대면 다른 환경에서 깨진다.

```gradle
// build.gradle
tasks.withType(JavaCompile).configureEach { options.encoding = 'UTF-8' }
```

```xml
<!-- pom.xml -->
<properties>
  <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
</properties>
```

이미 설정돼 있으면 건드리지 않는다.
