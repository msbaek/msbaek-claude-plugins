# 배움 반영 게이트 (anchor update)

구현 중 앵커 문서(템플릿 *.md의 규칙·예제)와 어긋나는 배움, 또는 테스트 목록에 없는
필요한 동작을 발견했을 때의 절차.
Spec Anchored의 핵심 규약 — 지속 갱신되는 문서(living document), 코드보다 먼저 갱신된다.

## 절차

1. **멈춘다** — 어긋난 채 코드를 먼저 고치지 않는다
2. **앵커를 먼저 갱신한다** — 해당하는 곳에:
   - 규칙이 틀렸거나 부족 → `## 규칙` 수정/추가 + `## 배움 로그`에 "규칙 N 변경: [한 줄]"
   - 예제 값이 틀림 → `## 예제` 표 수정 + 배움 로그 한 줄
   - 목록에 없는 필요한 동작 → 아래 "테스트 목록 갱신" 절차
   - 규칙·예제와 무관한 발견(구현 세부·기술 선택) → `## 배움 로그`에 한 줄만
3. **코드를 변경한다**
4. **같은 커밋에 담는다** — 앵커 갱신과 코드 변경을 분리하지 않는다
   (체크박스-커밋 동기화 규칙의 일반형)

## 사용자 질문 기준

- **규칙이 바뀌는 배움만** 사용자에게 질문한다 — 동작 계약이 바뀌므로
  (예: "취소 가능 기한이 명세와 달리 D+7이어야 할 것 같습니다")
- 나머지(배움 로그만 추가되는 발견)는 질문 없이 자율 기록한다

## Gherkin과의 관계

- `.feature` 파일이 시나리오의 실행되는 정본이다 — 시나리오가 바뀌는 배움이면
  `.feature`를 갱신하고, 앵커에는 배움 로그 한 줄만 남긴다
- 앵커 문서에 Gherkin 사본을 만들지 않는다

## 테스트 목록 갱신 (Canon TDD)

테스트 목록은 사이클마다 배움으로 갱신된다. 구현 중 목록에 없는 필요한 동작
(unlisted-but-required behaviour)을 발견하면 지금 작업을 끝낸 뒤가 아니라 발견 즉시
목록에 추가하고, 지금 하는 테스트에 계속 집중한다.

| 발견 | 목록 추가 위치 | 사용자 질문 |
|---|---|---|
| 기존 규칙의 새 예시(경계·조합·예외) | general: `## 예제 (검산표)`에 미구현 행(적용 규칙 번호 포함) / web-app: 세밀 분기면 예제 행, 외부 동작이면 `.feature` `@pending` 시나리오 | 하지 않는다(자율) |
| 어느 규칙에도 없는 새 동작 | 위와 같음 + `## 규칙` 추가 | 한다 — 규칙이 바뀌므로 위 기준과 같다 |
| 기존 행이 불필요·중복으로 판명 | 삭제하지 않고 배움 로그에 사유 한 줄 | 한다 — 허락 없이 테스트 삭제 금지 |

- 모든 추가는 `## 배움 로그`에 "목록 추가: [항목] — [발견 경위]" 한 줄을 남긴다
- 에이전트(`tdd-red`·`tdd-green`·`tdd-blue`)는 완료 보고에 `목록 추가: [항목 | 없음]`을
  반드시 적는다. 질문 대상인 추가는 문서에 쓰지 않고 보고만 한다(질문은 오케스트레이터 몫)
- 추가 행은 발견한 사이클의 커밋에 담는다(위 "같은 커밋" 규칙과 같다)

### 완료 판정 전 대응 점검

use case(또는 목록 전체) 완료를 선언하기 전에 두 가지를 확인한다.

1. **미구현 행 0개** — 사이클 중 추가된 행 포함
2. **규칙↔테스트 대응** — `## 규칙`의 모든 번호가 `## 예제` 행 또는 `.feature`
   시나리오 1개 이상에 등장하고, 그 행·시나리오를 검증하는 테스트가 존재한다.
   대응 테스트가 없는 규칙은 미구현 행으로 추가하고 사이클을 계속한다

## FAILURE CONDITIONS

- 앵커와 어긋난 코드 변경을 앵커 갱신 없이 커밋
- 앵커 갱신과 코드 변경을 다른 커밋으로 분리
- 규칙이 바뀌는 배움을 질문 없이 자율 반영
- 구현 중 발견한 필요한 동작을 목록에 추가하지 않고 배움 로그에만 기록
- 에이전트 완료 보고에 `목록 추가:` 필드 누락
- 대응 테스트가 없는 규칙이 남은 상태로 완료 선언
