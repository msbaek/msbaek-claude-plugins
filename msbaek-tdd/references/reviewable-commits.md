# Reviewable Commits & PRs — 의도 전달 표준 (SSoT)

> `/commit`(forward·작은 단위), `reconstruct-commits`(backward·히스토리 교정),
> `/compose-pr`(PR 텍스트 종합) **세 도구가 공유하는 단일 body 표준**이다.
> **이 문서는 CLAUDE.md에 `@`-import 하지 않는다** — commit/PR 작업 시에만 세 도구가
> 경로로 on-demand cite한다 (무관한 세션에 context tax를 물리지 않기 위해).

## 왜 이 표준이 존재하나 (목적)

- 코드는 What은 담아도 **Why는 못 담는다** — *정답만 있고 풀이 과정은 없는 시험지*.
- 진짜 프로그램은 코드가 아니라 저자의 **이론**(멘탈 모델, Peter Naur, *Programming as
  Theory Building*)이다. 이론이 있어야 **설명·진단·수정**이 가능하다.
- AI 시대의 병목은 코딩이 아니라 **검증**이다. 의도는 diff가 생성되는 순간 버려지고,
  리뷰어는 *기록되지 않은 의도를 재구성*하느라 441% 더 쓴다.
- 이 비용은 인간 인지의 한계가 아니라 **이미 생성된 의도를 포착·전달하지 못하는 툴링 문제**
  — 즉 *엔지니어링으로 제거 가능한 정보 손실*이다. 이 표준이 그 파이프라인이다.
- 단, 이 표준이 줄이는 건 "**how**(어떻게 구현했나)"의 재구성 비용뿐이다.
  "**whether**(애초에 옳은 변경인가)"의 판단은 영구히 사람(머지 소유자) 몫이다.

## 핵심 원칙 — Why를 박제하라

**메시지·PR은 What이 아니라 Why를 전달한다.**

- **What**(무엇을 바꿨나)은 diff가 이미 보여준다 → 메시지에서 반복하지 마라.
- 남길 것 셋:
  - **Why** — 이 변경이 왜 필요한가, 무엇을 해결하나.
  - **버린 대안** — 고려했으나 배제한 접근과 그 이유 (있을 때).
  - **결정 순서(추론)** — 어떤 이론·근거로 이 경로를 택했나. 코드 주석에 남긴 근거를
    메시지로 끌어올린다.

### 같은 diff, 다른 Why — 의도 구분 예시

`null` 체크 한 줄은 두 경우에 **What이 똑같이 보이지만 Why가 정반대**다. 메시지에
의도를 안 남기면 리뷰어가 옳은지 판단할 수 없다.

```java
// "없음 = 예외" — 없으면 안 되는 상황
User user = repository.findById(orderId.userId());
if (user == null) throw new UserNotFoundException(orderId);
// → FK로 보장되는 값이라 null은 데이터 무결성 위반 신호
```
```java
// "없음 = 값" — 없는 게 정상
Avatar avatar = repository.findAvatar(userId);
if (avatar == null) avatar = Avatar.DEFAULT;
// → 아바타 부재는 정상 상태, null을 기본값으로 대체
```

## Acceptance Criterion (이 표준의 합격선)

> **PR 텍스트 + "Files changed"만 가진 리뷰어가, 각 변경에 대해
> ⓐ 왜 했는지 ⓑ 무엇을 배제했는지 ⓒ 어떤 추론 순서로 도달했는지를 말할 수 있다.**

세 도구의 산출물은 모두 이 한 문장으로 자가 검증한다. 못 말하면 표준 미달이다.

## 4-Channel 모델 — 무엇을 어디에 남기나

의도·맥락을 남기는 채널은 넷이다. 같은 Why를 네 곳에 복붙하지 말고 **가장 가까운 채널
하나**에 두고 나머지는 그곳을 참조한다.

| 채널 | 담는 것 | 안 담는 것 |
|------|---------|-----------|
| **테스트 코드** | 인수조건·엣지 케이스, "이 동작이 왜 중요한가" | 구현 상세 |
| **커밋 메시지** | 이 커밋 **한 개 결정**의 Why + 버린 대안 짧게 (+ 선택: Decision-Log) | 여러 결정 뭉치, What 나열, 아키텍처급 근거 전체(ADR로) |
| **PR 메시지** | 커밋 내러티브 **종합** + 결정 로그 + 리뷰 가이드 | 커밋별 What 재나열 |
| **코드 주석** | 코드로 표현 못 하는 근거(왜 이 값·이 순서) | What 재진술 |

## 커밋 메시지 형식

```
type(scope): subject (50자 이내, 한국어, 의도 표현 — 왜 우선)

- <Why 문장 — 이 변경이 왜 필요한가 / 무엇을 해결하나. 문장마다 별도 줄. 72자 줄바꿈>

- <버린 대안 — 배제한 접근과 그 이유. 짧게 (있을 때만, Why와 blank line으로 분리)>

Decision-Log: 한 줄 요약           # 선택 — 이 커밋 단위의 짧은 결정 요약. compose-pr이
                                   #   PR의 "## 결정 로그"로 모아 종합한다. 불릿 없이
                                   #   git trailer 형식(Key: value) 유지
ADR: docs/adr/adr-NNNN-slug.md    # 선택 — 근거·대안 비교 자체를 ADR로 옮겼을 때만. 있으면
                                   #   본문의 "버린 대안"은 생략(ADR이 유일한 출처)
```

- type: `feat`/`fix`/`docs`/`style`/`refactor`/`test`/`chore`.
- **본문(Why·버린 대안)은 불릿(`- `)** — PR Layer 1과 동일하게 산문 벽 대신 짧은 불릿. Why가
  여러 문장이면 각각 별도 줄, 버린 대안은 Why와 blank line으로 나눠 별도 문단으로 둔다.
- **예외 없이 모든 본문 줄이 `- `로 시작** — Why/버린 대안 라벨을 안 붙이고 사실을 나열할
  때도(예: "무엇을 했다 / 무엇을 확인했다"류 요약) 각 사실은 줄바꿈만으로 묶지 않고 줄마다
  개별 불릿을 단다. 라벨 있는 본문뿐 아니라 라벨 없는 요약 본문에도 동일하게 적용.
- **Decision-Log·ADR은 불릿 없이** — git trailer 관례(`Key: value`)를 유지해 `git
  interpret-trailers` 같은 기계적 파싱 가능성을 남긴다. 본문과 blank line으로 분리.
- body는 항목 수에 집착하지 말고 **Why가 복원되는 데 필요한 만큼**. 사소한 변경은 한 줄도 OK.
- **기본값은 짧게**: Why 1~2문장이 기본. "버린 대안"·"결정 순서"는 실제로 저울질한 대안이
  있을 때만 쓴다 — 없는데 형식을 채우려고 지어내지 않는다.
- **4-channel 밖 섹션 금지**: "남은 일"·TODO·다음 단계 같은 항목은 이 형식(Why/버린 대안/
  Decision-Log/ADR)에 없다. 커밋 메시지에 넣지 말고 plan 문서·이슈로 보낸다.
- **아키텍처급 결정은 ADR로 승격, 본문엔 참조만**: 대안이 2개 이상인 아키텍처 결정(기준은
  `docs/session-mechanics.md`의 기존 ADR 제안 기준을 따름 — 여기서 새로 정의하지 않는다)은
  본문에 풀어쓰지 않는다. `adr-generator` 에이전트로 `docs/adr/adr-NNNN-slug.md`를 만들고
  커밋 본문엔 결론 한 줄 + `[ADR: ...]` 트레일러만 남긴다. 근거·대안 비교는 ADR이 유일한
  출처가 되고, 커밋·PR은 그곳을 참조한다(같은 내용 복붙 금지 — 4-channel 원칙과 동일).
- **분량이 늘어나면 재고**: 본문이 72자 줄바꿈 기준 4~5줄을 넘어가면 "이 결정이 정말 이만큼
  복잡한가"부터 의심한다. 아키텍처급이면 위 ADR 승격으로, 아니면 Why만 남기고 나머지는 쳐낸다.
- **작은 단위 원칙**: 한 커밋 = 하나의 결정 + 그 검증. 여러 결정을 한 커밋에 합치면
  Why가 뭉개진다. squash로 합치면 "같은 4개가 한 화면에 겹쳐" 순서·맥락이 사라진다.
- 한글 메시지는 **임시 파일 + `git commit -F`** (heredoc·`-m "한글"` 금지 — 깨짐).

### 예시 — 짧은 게 기본, 아키텍처급은 ADR 참조

짧은 예시(대부분의 커밋 — 버린 대안이 있어도 한 줄로 끝남):
```
fix(auth): 세션 만료 시 재로그인 리다이렉트 복구

- 리다이렉트 URL이 인코딩 안 돼 쿼리스트링이 잘렸다.
```

ADR 참조 예시(대안 2개 이상인 아키텍처급 결정 — 본문엔 결론만):
```
refactor(order): 재고 차감을 이벤트 발행 방식으로 전환

- 동기 호출은 재고 서비스 장애 시 주문 자체가 실패했다. 재시도 큐 등
  대안 비교와 선택 근거는 ADR 참조.

ADR: docs/adr/adr-0007-inventory-event-driven.md
```

Why·버린 대안이 여러 항목인 예시(트레일러까지 포함):
```
docs(japan-ddp): TDD 착수 전 일본 DDP 스펙·설계를 단일 출처로 통합

- 세관 다단계 계산 규칙이 원본 문서 3종에 흩어져 있었고, 그중 인수조건
  문서는 인라인 수치가 stale했다.
- red/green TDD 전에 이 근거를 스펙(0층 도메인 규칙 + 1층 AC)과 진행
  설계(3층 구조)로 통합해 이후 커밋이 참조할 단일 출처를 확정했다.

- 원본 3개 문서를 그대로 두고 커밋마다 개별 참조하는 방식도 검토했으나,
  문서 간 수치 불일치를 매번 교차 확인해야 해서 배제했다.

Decision-Log: 세관 규칙(0층)·AC(1층)는 problem space로 먼저 확정하고,
use case(3층)는 구현 직전으로 미룬다
```

## PR 제목 형식 (compose-pr 산출)

```
{branch-name} | {intent 중심 제목}
```

- `branch-name`은 현재 브랜치명을 그대로 사용(재작성·축약 금지).
- 제목은 짧고 명확하게, 구현 상세 나열이 아니라 **왜 이 PR이 존재하는가**를 표현.

## PR 메시지 형식 (compose-pr 산출)

**두 청중을 한 문서로 충족한다** — 인간 리뷰어(머지 판단: 빠른 스캔)와 AI·심층 리뷰(맥락 복원:
전체 정보). 그래서 body는 **2레이어**다: 인간용 요약을 위에 펼쳐두고, 심층부는 `<details>`로
접는다. GitHub이 `<details>`를 네이티브 접기로 렌더하므로 **인간은 기본 간결·1클릭으로 펼침,
AI 리뷰어는 raw markdown body로 접힘 내부까지 전부** 읽는다(숨김 아님).

커밋을 **순서대로 따라 읽으면 맥락이 누적되도록** 종합한다. **모든 섹션은 산문 벽이 아니라
짧은 불릿**(아래 "표현 규칙" 준수) — **라벨 붙은 항목(선택/대안/포기, 이슈/배경/목적 등)은 각각
별도 불릿 한 줄**로 쓰고, 여러 라벨을 한 불릿에 몰아넣지 않는다(mercury 4섹션 스타일). 값이 없으면
빈칸·"TBD" 대신 `해당 없음` + 짧은 이유.

### Layer 1 — 인간 머지 판단 (항상 펼쳐짐)

- `## Why` — 왜 이 변경이 필요한가. 불릿(예: 이슈/배경/목적). **첫 항목 = 비즈니스 동기**(애초에
  왜 이 PR이 필요했나 — 운영 부담·컴플라이언스·PII·장애·정책·리스크). "Why 이중 채널"을 따른다.
- `## Trade-off` — **머지 판단에 필요한 핵심 선택 하나.** `- 선택:` / `- 대안:` / `- 포기한 것:`을
  **각각 별도 불릿**으로(한 불릿에 몰지 말 것). 전체 결정 목록이 아니다(그건 Layer 2 결정 로그).
  실질적 절충이 없는 변경이면 이 섹션 생략.
- `## Blast Radius` — 영향 범위를 구체 이름으로. 영향 컴포넌트 / 영향 비즈니스 로직 /
  데이터·API 영향(스키마·엔드포인트·flag).
- `## Check & Rollback` — 검증(무엇으로 확인했나) / 배포 후 확인 / 롤백 방법 / Feature Flag 여부.
  (게이트 증거 dry/crap/mutation과는 별개 — 그건 Layer 2 `## 검증`.)

> **Layer 1 배치 원칙:** 머지 판단(whether)에 필요한 것만 올린다. 핵심 절충 하나는 Trade-off로,
> 안전·정확성 critical 결정(예: 사용 중인 것을 잘못 막지 않도록 제외)은 **절충이 아니어도 그 결과를
> Blast Radius/Check & Rollback에 드러낸다.** 그 상세 근거·나머지 결정은 Layer 2 결정 로그로.

### Layer 2 — AI + 심층 리뷰 (`<details>`로 접힘, 규모 작으면 통째 생략)

```markdown
<details><summary>🔍 심층 리뷰용 — 커밋 내러티브 · 결정 로그 · 리뷰 가이드</summary>
...
</details>
```

- `## 커밋 내러티브` — 커밋별 1~2줄. "이 단계가 무엇을 푸는가"를 의존성·이론 순서로.
- `## 결정 로그` — Layer 1 Trade-off 외 나머지 결정 전부: 배제한 대안, 트레이드오프,
  되돌릴 수 없는 선택의 근거.
- `## 리뷰 가이드` — 어디부터 어떤 순서로 볼지, 주의 깊게 볼 곳.
- `## 검증` — 아래 게이트 증거 규칙을 따른다 (조건부). 실행 안 했으면 이 섹션을 만들지 않는다.

## Why 이중 채널 — 표면 Why vs 진짜 Why

`## Why` 첫 항목(비즈니스 동기)은 **코드에서 복원한 "그럴듯한 Why"를 진실로 착각하지 않는다.**
위험은 "Why 부재"만이 아니라 — **Why가 있어 보이지만 그게 표면 proxy고, 진짜 동기가 한 겹 아래
코드 밖(작성자 머릿속·컴플라이언스 맥락)에 있는** 경우다.

- **Provide(당김):** 작성자가 Why를 미리 제공하면 그대로 첫 항목에 쓰고 아래 Ask는 건너뛴다.
- **Ask(밀기, 매 PR):** 그 외에는 **항상** 초안 Why를 작성자에게 확인한다 — *"이게 진짜 동기가
  맞나? 코드 밖에 있는 상위 동기(PII·컴플라이언스·보안·리스크)가 따로 있나?"* 받은 답을 첫 항목으로.
  how-Why(구현을 왜 이렇게)는 커밋·주석에서 끌어올려도 되지만, why-at-all(애초에 왜 이 변경)은
  종종 기록 밖이라 이 확인이 그 구멍을 막는다.

### 표면 Why vs 진짜 Why — 예시 (why-at-all 축)

같은 변경(미사용 보고서 요청 차단, ktown4u/bo#50)의 Why가 코드에서 읽히는 것과 진짜 동기가 다르다.

- **표면 Why (코드·커밋에서 복원):** "이 보고서들은 아무도 안 쓰는데 조회 가능한 채 남아 유지·문의
  비용만 든다." ← 그럴듯하지만 부차적.
- **진짜 Why (작성자·컴플라이언스 맥락):** "미사용 보고서 상당수가 **개인정보(PII)를 포함**한 채
  조회 가능 — **망분리 환경 이전 전에 노출 지점을 최소화**해야 한다." ← AI가 diff에서 못 찾는다.
  Ask 채널로 작성자에게 물어야 복원된다.

> null-check 예시(위)가 *how-Why*(같은 What, 구현 의도가 정반대) 축이라면, 이 예시는
> *why-at-all*(애초에 왜 필요했나가 코드 밖) 축이다. 둘은 상보적이다.

## 표현 규칙 (PR 본문 — 리뷰 대상)

PR 본문은 구어·비유 표현을 처음부터 배제한다 (글로벌 CLAUDE.md "명확한 단어" 원칙).

- **비유적·구어 동사 금지** — "끼우다/박다/꽂다/물리다/태우다" → "추가하다/넣다/두다/적용하다".
- **자작 도구화 명사(~기) 지양** — "감지기/처리기/검증기" → 코드에 실재하는 이름 또는 명확한 표현.
- **한 대상은 한 용어로 통일** — 같은 것을 여러 이름으로 섞지 않는다. **출력 직전 self-check.**

## 게이트 증거 (조건부 — 강제 아님)

`dry`(중복) / `crap`(복잡도×커버리지) / `mutation`(테스트 실효성) 같은 결정론적 게이트는
**이 작업에서 실제로 실행했을 때만** 그 결과를 검증 증거로 포함한다.

- 실행하지 않았으면 `## 검증` 섹션을 **만들지 마라** — 돌리지 않은 게이트를 "통과"로
  표현하는 것은 금지.
- 게이트는 자동 실행·강제하지 않는다. **사용자가 명시적으로 요청할 때만** 실행한다.
