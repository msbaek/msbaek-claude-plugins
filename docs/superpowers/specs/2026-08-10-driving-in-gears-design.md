# msbaek-tdd: Driving In Gears (기어 모델) 설계

- 날짜: 2026-08-10
- 출처 개념: Kent Beck "driving in gears" (『TDD By Example』) 및 "Coding Agents: Driving In Gears" 글
- 상태: 설계 승인됨 (구현 전)

## Goal (testable)

`/tdd-rgb`에 기어(low/mid/high) 개념을 도입해, 사용자 검토 지점의 밀도를 확신(confidence)과
폭발 반경(blast radius)에 따라 조절할 수 있게 한다.

성공 기준:

1. `--gear` 미지정 실행은 기존과 문자 그대로 동일하게 동작한다 (low = 현행).
2. mid에서 한 테스트의 R→G→B가 중간 대기 없이 진행되고, 사이클 완료 후 1회 대기한다.
3. high에서 전체 테스트 목록을 자율 진행한 뒤 적대적 리뷰가 실행되고, 리뷰 통과 후에만
   최종 사용자 검토를 요청한다.
4. 기어 전환 제안은 정의된 신호가 감지될 때만 나타난다.
5. 템플릿 문서에 기어 상태·전환 이력이 기록되고, `/tdd` 상태 분석이 이를 복원한다.

## Constraints (non-negotiable)

- **기어는 검토 지점의 밀도만 바꾼다.** TDD 3법칙, 한 번에 테스트 하나, phase별 커밋
  (`test:`/`feat:`/`refactor:`), 테스트 삭제 금지 등 나머지 Hard Rule은 모든 기어에서 동일.
- 기어 전환 결정은 항상 사용자가 내린다. 오케스트레이터는 제안만 한다.
- R/G/B agent 3개(tdd-red, tdd-green, tdd-blue)는 수정하지 않는다. 검토 대기는
  오케스트레이터(tdd-rgb SKILL.md)의 책임이다.
- 하위 호환: 기어 필드가 없는 기존 프로젝트 문서는 low로 간주한다.

## 섹션 1: 기어 정의와 검토 지점

호출 형식: `/tdd-rgb [plan-doc-path] [--gear=low|mid|high]` — 기본값 `low`.

| 기어 | 검토 지점(사용자 피드백 대기) | 대응 상황 |
|---|---|---|
| **low** | Red 후 · Green 후 · Blue 후 (현행 그대로) | 이론에 확신 없음, 낯선 도메인·기술, 학습 목적 |
| **mid** | 테스트 1개의 R→G→B 사이클 완료 후 1회 | 유사 문제 경험 있음, 작동하는 이론을 빠르게 확보할 것으로 기대 |
| **high** | 전체 테스트 목록 완료 + 적대적 리뷰 통과 후 최종 1회 | 이론이 상용구(boilerplate) 수준으로 명확 |

phase별 커밋은 기어와 무관하게 각 agent가 수행하므로, high에서 문제가 발견돼도
테스트 단위로 revert할 수 있다.

## 섹션 2: 기어 전환 — 신호 · 제안 · 기록

사이클 사이에 오케스트레이터가 신호를 점검하고, 감지 시 전환을 **제안**한다.

**업시프트 신호** (low→mid, mid→high):

- 최근 2~3 사이클 연속으로 사용자 피드백이 "그대로 진행"뿐이었음
- 설계 안정 — Blue phase에서 새로운 통찰이 더 이상 나오지 않음
- 남은 테스트가 기존 패턴의 반복

제안 문구에 원문 경고를 내장한다: "지루함은 업시프트를 얻어냈다는 정직한 신호지만,
조급함은 그렇지 않습니다."

**다운시프트 신호** (high→mid, mid→low):

- revert 발생
- 예상과 다른 이유의 테스트 실패 반복
- 구현이 불투명 — 사용자 이견·질문 반복
- Green phase에서 최소 구현 범위를 넘는 코드 생성 감지

**기록**: 템플릿 문서(예: `BowlingGame.md`)의 진행 기록 섹션에
`기어: mid (사이클 7에서 low→mid, 사유: 설계 안정)` 형태로 이력을 남긴다.
`/tdd` 상태 분석이 이를 읽어 세션 재개 시 기어를 복원한다.

## 섹션 3: high 기어의 적대적 리뷰

high 기어에서 전체 테스트 목록이 green이 되면, 최종 사용자 검토 전에 적대적 리뷰를
**의무 단계**로 실행한다.

1. **리뷰어 선택**: `adversarial-reviewer` agent(사용자 환경 `~/.claude/agents/`)를
   1순위로 사용한다. 없는 환경에서는 general-purpose sub-agent에 SKILL.md 내장
   적대적 프롬프트로 dispatch한다(플러그인 이식성). 내장 프롬프트 요지 — "이 diff를
   깨뜨릴 구체 시나리오를 찾아라: 테스트가 검증하지 않는 동작, 테스트 목록과 구현의
   표류(drift), 최소 구현을 가장한 과잉 구현, 코드 스멜."
2. **입력**: 시작 커밋..HEAD diff + 테스트 목록 문서(intent 요약).
   adversarial-reviewer가 depth 보정에 intent를 사용한다.
3. **결과 처리**: 지적 사항을 심각도별로 분류해 사용자에게 보고. 수정이 필요한 항목은
   사용자 승인 후 반영하며, 반영도 RGB 규칙을 준수한다(실패 테스트 먼저).
4. **Definition of Done**: green 스위트 + 적대적 리뷰 통과. 그 후에야 최종 사용자
   검토를 요청한다.

## 섹션 4: 폭발 반경(blast radius) 경고

`/tdd-rgb` 시작 시와 업시프트 제안 시, 오케스트레이터가 대상 코드 영역에서 high-stakes
신호를 점검한다: 인증/인가, 결제/금액 계산, 데이터 삭제·변경(마이그레이션), 외부 API 호출,
동시성.

감지 시 경고한다:

> "이 작업은 폭발 반경이 큽니다(예: 결제 금액 계산). 확신이 높아도 한 단 낮은 기어를
> 권장합니다: high → mid. 틀릴 확률이 낮아도 틀렸을 때 비용이 큽니다."

경고 후 결정은 사용자가 내린다. high-stakes 영역에서는 업시프트 제안 자체를 억제한다
(다운시프트 제안은 정상 동작).

## 섹션 5: 변경 범위 · 검증

**수정 파일 2개** (agents 3개·나머지 스킬 무변경):

| 파일 | 변경 내용 |
|---|---|
| `msbaek-tdd/skills/tdd-rgb/SKILL.md` | 기어 파라미터 파싱, 기어별 검토 지점 표, 전환 신호·제안, 적대적 리뷰 단계, 폭발 반경 경고, fallback 적대적 프롬프트. 피드백 규칙(Hard Rule)을 "기어가 정의하는 검토 지점에서 반드시 대기"로 재정의 |
| `msbaek-tdd/skills/tdd/SKILL.md` | 템플릿 진행 기록 섹션에 기어 필드 1줄, 상태 분석 시 기어 복원·안내 |

**작업 위치**: 이 repo(`msbaek-claude-plugins`)의 `feat/driving-in-gears` 브랜치.
클린룸 검증(msbaek-tdd-validation-cart)이 진행 중이므로 검증 회차 완료 후 main에 머지한다.

**검증(승인 조건)**: Goal의 성공 기준 1~5를 시나리오로 확인한다. 자동화된 테스트 하네스가
없는 마크다운 스킬이므로, 검증은 실제 `/tdd-rgb` 실행 관찰(또는 클린룸 검증 다음 회차)로
수행한다.

## 버린 대안

- **references/gears.md 분리** (B안): SKILL.md 비대화는 막지만, 검토 지점 제어는 매
  사이클의 핵심 제어 흐름이라 참조 파일을 읽지 않고 진행하는 누락 모드가 생긴다. 기각.
- **자동 기어 전환**: 빠르지만 "조급함이 아니라 지루함이 신호"라는 원문 경고와 충돌. 기각.
- **hunk-reviewer 사용**: 라이브 hunk 세션 전제의 도구라 자율 진행 후 일괄 리뷰 용도에
  부적합. 기각.
- **설계 단계(tdd-plan)까지 적용**: 원문은 설계 전략도 기어별로 제시하지만, 변경 범위를
  줄여 검증 가능하게 tdd-rgb만 우선 적용. 이후 확장 가능.
